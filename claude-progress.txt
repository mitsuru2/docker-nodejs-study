## 2026-09-19: Fix Issue #49 - Disable dark mode support

- Root cause: PrimeNG's `providePrimeNG` theme options defaulted to
  `darkModeSelector: 'system'`, which applies the CustomPreset's dark
  color-scheme tokens whenever the browser/OS reports
  `prefers-color-scheme: dark`. The homepage should always render in
  light mode regardless of the browser/OS theme setting.
- Fix: explicitly set `darkModeSelector: 'none'` under
  `theme.options` in the `providePrimeNG(...)` call in
  `src/app/app.config.ts`. This config (`commonConfig`) is shared by
  both the browser and server (SSR) app configs, so the fix applies
  uniformly.
- `src/index.html` already declared `<meta name="color-scheme"
  content="light">`, so native browser chrome (scrollbars, form
  controls) was already light; the PrimeNG theme tokens were the only
  remaining dark-mode source.
- Verified manually with Playwright: loaded the homepage under both
  `colorScheme: 'dark'` and `colorScheme: 'light'` context emulation.
  Screenshots are pixel-identical; `getComputedStyle(document.body).colorScheme`
  reports `"light"` in both cases.
- `npm test` (30/30) and `npm run build` both pass.
- No unresolved issues.

## 2026-09-19: Fix Issue #51 - Per-issue Google Drive subfolder for test evidence

- Root cause: scripts/attach-issue-evidence.sh uploaded every test-evidence
  zip directly into the root of the shared GDRIVE_FOLDER_ID, so zips from
  different issues piled up together in one flat folder with no way to
  tell which zip belonged to which issue at a glance.
- Fix: before uploading, the script now looks up (via a Drive API
  `files.list` query scoped to `'<GDRIVE_FOLDER_ID>' in parents`) a
  subfolder named `issue-<issue-number>`. If it already exists, its id is
  reused; otherwise the script creates it with `files.create`
  (`mimeType: application/vnd.google-apps.folder`, parented under
  GDRIVE_FOLDER_ID). Every zip for that run is then uploaded with that
  subfolder as its parent instead of GDRIVE_FOLDER_ID directly.
- scripts/init-verify-gdrive.sh was left unchanged — it only checks that
  GDRIVE_* credentials are valid and the Drive API is reachable, it does
  not touch folder structure.
- Verified directly against the real Google Drive API in a throwaway
  script (not the full attach-issue-evidence.sh, to avoid posting a real
  issue comment while testing): created a test subfolder, confirmed a
  second lookup call deterministically returns the same folder id
  (idempotent — reruns for the same issue won't create duplicate
  subfolders), uploaded a file into it and confirmed the Drive API
  response's `parents` pointed at the subfolder, then deleted the test
  folder to leave the real Drive folder clean.
- `npm test` (30/30) and `npm run build` both pass.
- No unresolved issues.

## 2026-09-19: Fix Issue #54 - Back to home screen by clicking title text

- Feature request: clicking the app-shell title text (`labels.common.title1`
  / `labels.common.title2`) should navigate back to the home screen, in both
  PC and mobile layouts, with the mouse cursor changed to a pointer.
- Fix: wrapped the existing title markup (both the PC single-line `<h1>`
  and the mobile two-line `<h1>` + `.sub-title` block) in a single `<a
  class="title-link" [routerLink]="homeLink">` anchor in
  src/app/feature/app-shell/app-shell.html. Added `RouterLink` to the
  standalone component's `imports` and a `protected readonly homeLink =
  '/' + PagePath.Home` field in src/app/feature/app-shell/app-shell.ts.
  Using a native `<a routerLink>` (rather than a `(click)` handler on a
  `<div>`) gives keyboard focus/activation and correct link semantics for
  free, without any extra ARIA wiring.
- Added `[attr.aria-label]="labels.common.home"` on the anchor so screen
  readers announce it as the existing "ホーム" (Home) label rather than
  reading out the full title/subtitle text as a link name.
- src/app/feature/app-shell/app-shell.scss: added a `.title-link` rule
  (`color: inherit; text-decoration: none; cursor: pointer;`) so the
  anchor doesn't pick up default blue/underline link styling while still
  showing the pointer cursor required by the issue. Left the browser's
  default focus outline untouched for keyboard-focus visibility.
- Verified with Playwright against `ng serve` (both a 1280x800 desktop
  viewport and a 390x844 mobile viewport): starting from `/ja/career`,
  clicking the title anchor navigates to `/ja/home` in both layouts;
  `getComputedStyle(...).cursor` on the anchor reports `"pointer"` in
  both layouts; no console errors. Also ran `@axe-core/playwright`
  against both viewports before and after the change (diffed against the
  pre-change baseline) — the only AXE violations present
  (`landmark-one-main`, `region`, plus a couple of unrelated pre-existing
  content issues on the career/home pages) already existed before this
  change (previously anchored on the bare `h1`/`.main`/`.footer`
  elements); no new violation categories were introduced by wrapping the
  title in the anchor.
- `npm test` (30/30), `npm run lint` ("All files pass linting."), and
  `npm run build` all pass.
- No unresolved issues.

## 2026-09-21: Fix Issue #57 - Career page responsibility table wrongly centered on mobile/tablet

- Root cause: `src/app/feature/app-shell/app-shell.scss` sets `.main {
  text-align: center; }` inside the `@include v.tablet` mixin (`max-width:
  970px`), which also covers the mobile breakpoint (570px) since it's a
  subset. This app-shell wrapper surrounds all page content, so the
  centered text-align was inherited by every descendant on tablet/mobile
  widths — including the normal (non-header) cells of the "responsive
  table" used on the career page (`src/app/feature/experience`) to show
  company/project details (事業内容, 売上高, 従業員数, 概要, 担当工程,
  実績, etc.).
- Fix: added a scoped override in
  `src/app/feature/experience/experience.scss`: `.cell:not(.header) {
  text-align: left; }` inside the existing `.responsive-table` rule
  block. This only affects non-header cells, leaving header cells'
  existing (correct, per the issue) centered appearance on tablet/mobile
  untouched, and has no effect on PC width where `.main` was never
  centered in the first place (its cells already computed to `left`
  there).
- Verified with Playwright against `ng serve` at three viewports (PC
  1280px, tablet 800px, mobile 390px): read `getComputedStyle(...).textAlign`
  on the first three header/value cell pairs of the responsibility
  table. Before the fix, header and normal cells both computed to
  `center` on tablet/mobile; after the fix, header cells still compute to
  `center` (tablet/mobile) / `start` (PC, native default), and normal
  cells now compute to `left` at all three widths. Screenshots taken at
  all three viewports confirm the visual left alignment. Also ran
  `@axe-core/playwright` at tablet and mobile widths — the only
  violations present (`landmark-one-main`, `region`) are the same
  pre-existing, unrelated ones noted in earlier sessions; no new
  violation categories were introduced.
- `npm test` (30/30), `npm run lint` ("All files pass linting."), and
  `npm run build` all pass.
- No unresolved issues.
